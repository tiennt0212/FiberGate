## Architecture & Tech Stack

[2026-07-01] **Product framing pivot**: Pivoted FiberGate from a managed custodial LSP (multi-customer SaaS) to a self-hosted open-source infrastructure framework — a docker-compose bundle (Fiber node + PostgreSQL + FiberGate core: Next.js dashboard + API), where each merchant deploys `docker compose up -d` themselves and keeps their own node/data — Reason: The "Gone in 60ms" hackathon rules clearly state "infrastructure only, not products built on top"; a multi-customer custodial SaaS model risks being miscategorized and losing points.

[2026-07-01] **Auth model**: Dropped the multi-tenant API key system (`profiles`/`api_keys` table, per-client bcrypt `secret_hash`, BR-SEC-004 user_id scoping). Replaced with a simple internal auth layer: a single shared secret `FIBERGATE_INTERNAL_SECRET` (same pattern as the existing `CRON_SECRET`), compared constant-time, used by the merchant's storefront app to call into FiberGate core when the two services don't run on the same host/network — Reason: In a self-hosted setup, each deployment serves exactly one merchant, so distinguishing multiple clients is redundant; a minimal internal auth is still needed so core can't be called without authorization when the container is exposed on a separate network.

[2026-07-01] **Database**: Dropped Supabase (including the self-hosted variant), switched to plain PostgreSQL (its own container) + Drizzle ORM — Reason: The official self-hosted Supabase bundle packages ~10 containers (gotrue, postgrest, realtime, storage, kong, studio...), far too heavy for the "3 lightweight containers" goal of the docker-compose bundle; single-tenant means Supabase Auth/RLS isn't needed.

[2026-07-01] **Dashboard auth**: Uses a single-admin password gate (set via env var at deploy time, bcrypt-hashed, httpOnly session cookie) instead of Supabase Auth/multi-user login — Reason: Each deployment is operated by exactly one merchant, so no user/role system is needed.

[2026-07-01] **Fiber client SDK**: `lib/fiber/client.ts` is built on top of `@ckb-ccc/fiber` (the official SDK), without hand-rolling raw JSON-RPC, and without using `@fiber-pay/sdk` for the core flow — Reason: `@ckb-ccc/fiber` is the official SDK recommended by the hackathon ("best starting point for app integrations"); `@fiber-pay/sdk`/`@fiber-pay/react` are community/experimental and riskier for the core flow (Phase 1/2). `@fiber-pay/sdk` is kept as a reference for Phase 3 (L402) since the `fiber-l402` demo uses exactly this library.

[2026-07-01] **Phase 2 real-time listener — verified**: Confirmed that FNN has a `pubsub` RPC module (methods `subscribe_store_changes`/`unsubscribe_store_changes`, notification `store_changes`), present since stable v0.8.1 (not only on the develop branch), officially documented at `fiber.world/docs/api-reference#websocket-subscriptions`. The node fires `StoreChange::PutCkbInvoiceStatus { payment_hash, invoice_status }` exactly when an invoice changes status — Reason for choosing this for Phase 2: this is the only way to avoid periodic polling, matching the instant-payment speed of the Fiber Network. Known constraints: (a) the official docs explicitly state the intended purpose is for the Cross-Chain Hub, not a general client — treat this as "off-label usage," still keep a low-frequency poll fallback (30-60s); (b) `@ckb-ccc/fiber` doesn't support subscriptions (verified against the real npm source) — a dedicated WebSocket JSON-RPC client needs to be written for this; (c) enabling Biscuit auth would require the additional `read("cch")` permission, but since `fiber-node` only binds internally within the docker network (no public IP), Biscuit auth is expected to stay disabled, so this constraint doesn't arise in the default setup.

[2026-07-02] **SDK package naming — fixed a contradiction**: Confirmed the official package name is `@fibergate/sdk` (matching `.context/INDEX.md`, `system-design.md`, and the issue #2 checklist — 3/4 sources agree). `CLAUDE.md`'s monorepo layout line had mistakenly written `@fiber-gateway/sdk` — fixed within the same session — Reason: CLAUDE.md claims to be the single source of truth, so once the discrepancy was found, CLAUDE.md was corrected to match the majority of the other sources rather than keeping it as-is and fixing the other files.

[2026-07-02] **fiber-node container — build strategy** (issue #3, docker-compose bundle): Use the **official Docker image** `nervos/fiber` (Docker Hub) / `ghcr.io/nervosnetwork/fiber` (GHCR mirror) for the `fiber-node` service, instead of building FNN from source or packaging a prebuilt binary ourselves — Reason: the `nervosnetwork/fiber` repo (`docker/README.md`, confirmed directly via `gh api`) publishes an official image that already bundles `fnn-cli` and auto-copies the bundled testnet config to `/fiber/config.yml` on first run — much simpler and lower-risk than building/maintaining our own Dockerfile for FNN. Constraint discovered: the image repo **currently has no stable semver tags** (only `0.9.0-rc1`..`rc6` prereleases and `sha-<hash>`) even though GitHub release `v0.8.1` exists — temporarily pinned to `nervos/fiber:0.9.0-rc6` (latest tag with a real image), needs revisiting once a stable tag exists. Important gotcha: the RPC listener in the bundled testnet config defaults to binding `127.0.0.1:8227` (loopback-only) — `docker/fiber-node/config.yml` had to be pre-seeded with `rpc.listening_addr: 0.0.0.0:8227` for `fibergate-core` to be able to reach it over the internal Docker network; otherwise it would be silently unreachable even with correct `depends_on`/network settings.

[2026-07-02] **Base images for docker-compose** (issue #3): `node:20-alpine` for `docker/fibdergate-core/Dockerfile` (fibergate-core), `postgres:16-alpine` for the `postgres` service — Reason: Node 20 is the current LTS, Postgres 16 is the most recent stable release; no CKB toolchain constraint requires a different base image, and Alpine was chosen to keep images small, matching the "3 lightweight containers" goal already settled in the "Database" decision above.

[2026-07-02] **`docker/fiber-node/config.yml` — fixed incorrect provenance** (found while re-reviewing issue #3 after merge): The initially committed config was fetched via `gh api .../contents/config/testnet/config.yml` **without `?ref=`**, i.e. it pulled the default branch HEAD instead of the correct `v0.9.0-rc6` tag (matching the pinned Docker image tag `nervos/fiber:0.9.0-rc6`) — the two versions genuinely diverge (HEAD has extra SOCKS5/Tor proxy options not present in `v0.9.0-rc6`). Re-fetched with the correct `?ref=v0.9.0-rc6`, keeping only the one intentional change (`rpc.listening_addr: 127.0.0.1` → `0.0.0.0`) — Reason: fetching config without pinning the correct ref is a silent schema-mismatch risk; general principle: any resource fetched from an external repo must pin the exact ref matching the version actually running.

[2026-07-02] **`FIBER_SECRET_KEY_PASSWORD` — added to `.env.example`** (found while re-reviewing issue #3 after merge): This variable had previously been intentionally excluded from `.env.example` (to keep the "7 FiberGate app-level variables" concept separate from "fiber-node's own secret"). Decision reversed: still add a template line for it, but in its own section with a comment clearly explaining it is **not** one of the 7 app-level variables — Reason: keeping the concepts separate doesn't require excluding it entirely from the sample file; a merchant following the main flow (`cp .env.example .env`) would previously see this variable nowhere at all, easy to miss since the only mention lived in a standalone prose line in `docker-compose.yml`/`README.md`. Synced updates: `.env.example`, `README.md` ("Generating secrets" is now 5 variables), `system-design.md`.

[2026-07-02] **`DATABASE_URL` auto-derived from root `POSTGRES_*`** (step 1/2, later superseded by the "single code path" decision below): Removed the manually-entered `DATABASE_URL=` field from the root `.env.example` — Original reason: this was a duplicate-value bug **within the same file** — `DATABASE_URL` and the 3 `POSTGRES_*` variables both encoded the same information (credentials) in the shared root `.env.example`, so updating one and forgetting the other would produce a hard-to-diagnose auth error.

[2026-07-02] **Renamed `FIBER_NODE_SECRET` → `FIBER_NODE_RPC_AUTH_TOKEN`** (human picked directly in conversation, among 4 proposed options): The app-level Biscuit token variable (optional, used when calling RPC on fiber-node) was easily confused with `FIBER_SECRET_KEY_PASSWORD` — a node-level variable whose name is dictated by the `nervos/fiber` image itself and can't be changed. Renamed to something that more clearly conveys its purpose (RPC auth token) without hard-coding a specific Biscuit mechanism into the name — Reason: reduce the risk of confusing two very different concepts (auth for the app calling RPC vs. the password unlocking the CKB signing key) scattered across multiple files (`.env.example` x2, `docker-compose.yml`, `system-design.md`).

[2026-07-02] **Added the `fiber-node-preflight` service** (human chose "both" between "just improve the docs" and "add a preflight check," i.e. do both): Added a one-shot service using `alpine:3.20` that checks `docker/fiber-node/ckb/key` exists before `fiber-node` is allowed to start (`depends_on: condition: service_completed_successfully`), printing a clear human-readable message if it's missing instead of letting `fiber-node` crash-loop with a hard-to-read Rust panic — Reason: a merchant deploying for the first time who forgets the CKB key creation step would see a confusing error without a preflight; live-verified both branches (missing key → exit 1 with a clear message; key present → passes). README was also updated with corresponding Prerequisites + Troubleshooting sections.

[2026-07-02] **`apps/web/.env.local` switched to `POSTGRES_USER/PASSWORD/DB/HOST/PORT`** (step 2/2, human chose directly between "keep DATABASE_URL as-is" vs. "switch to POSTGRES_*"): The main goal was to align the pattern between the two env files, not because `DATABASE_URL` was "no longer used" — the variable is still genuinely used, only who assembles the connection string changes. Previously root used the `POSTGRES_*` set (derived through compose) while `apps/web` used `DATABASE_URL` (typed by hand) — two different patterns for the same concept. `POSTGRES_HOST`/`POSTGRES_PORT` had to be added separately for `apps/web` (defaulting to `localhost:5432`) since local dev can point at any Postgres instance, unlike the fixed topology inside docker.

[2026-07-02] **Final call: drop `DATABASE_URL` entirely everywhere (including `docker-compose.yml`), always let the code assemble it** (human made the final call directly, superseding the approach in the two decisions immediately above): `docker-compose.yml`'s `fibergate-core.environment` no longer assembles `DATABASE_URL` via `${VAR}` interpolation — instead it passes the 5 raw variables `POSTGRES_USER/PASSWORD/DB/HOST/PORT` directly (with `HOST=postgres`, `PORT=5432` as fixed values declared in `docker-compose.yml`, not `.env.example` fields). `lib/db/` (not yet written) now has **exactly one code path** for building the connection string, shared between running in Docker and `pnpm dev` outside Docker — no longer distinguishing "root derives via compose, apps/web derives via code" as in the previous two decisions. Reason: simplify down to a single mechanism, reduce the surface that needs explaining in `system-design.md`, and reduce the risk of two parallel mechanisms drifting apart later.

[2026-07-02] **Added `dotenv-cli` as a dev dependency of `apps/web`, merging root `.env` + `apps/web/.env.local` for local dev** (human confirmed adding the new dependency directly in conversation, after I asked and received clear agreement — following the process CLAUDE.md requires for "adding a new dependency"): `apps/web/package.json`'s `dev` script changed from `next dev` to `dotenv -e .env.local -e ../../.env -- next dev`. Live-verified: `dotenv-cli`'s "first file listed wins" behavior (per the official docs, not "last wins" — easy to get backwards), so `.env.local` must come before `../../.env` in the command for the override to work correctly; tested `next dev` starting successfully with this setup. Consequence: `apps/web/.env.example` shrank to exactly the 3 variables that genuinely differ between Docker/local dev (`POSTGRES_HOST`, `POSTGRES_PORT`, `FIBER_NODE_URL`) instead of duplicating all 10 variables as before — root `.env` is now the single source of truth for the shared variables (`POSTGRES_USER/PASSWORD/DB`, `ADMIN_PASSWORD_HASH`, `FIBERGATE_INTERNAL_SECRET`, `FIBER_NODE_RPC_AUTH_TOKEN`, `WEBHOOK_SIGNING_KEY`, `CRON_SECRET`). `docker-compose.yml` didn't change at all — Docker Compose already reads the root `.env` via its built-in convention, no `dotenv-cli` needed. Reason: drastically reduce secret duplication between the two files, the root cause of the entire `DATABASE_URL`/pattern-alignment discussion thread in the decisions above.

[2026-07-02] **`.env.example` pre-filled `CHANGE_ME_*` placeholders + a `secrets-preflight` service — DONE, THEN REVERTED, see the decision immediately below** (kept for history, not deleted — this approach turned out to be too verbose, so direction changed within the same session): At one point 4 variables `CHANGE_ME_<VAR_NAME>` were added along with a one-shot `alpine` service that would block `postgres`/`fibergate-core` if any placeholder remained. A memorable bug surfaced during implementation (still worth documenting even though the code was reverted): Docker Compose auto-interpolates `$VAR`/`${VAR}` across the ENTIRE string in the YAML, including inside a multi-line `command: |` block — the script's own internal shell variables (`$val`, `$var`) were misinterpreted by Compose as unset compose variables and silently replaced with empty strings, making the check falsely pass (a silent bug). If a shell script inside any service's `command:` is ever needed again, remember to escape every shell-runtime `$` as `$$`.

[2026-07-02] **Reverted `secrets-preflight`, went back to leaving the 4 required variables blank, moved generation instructions to README.md** (human made the final call directly, superseding the decision immediately above): Adding an entire service just to validate `.env` values was judged too heavyweight for the benefit gained. Reverted to the simple pattern: leave them blank (no placeholder), let `docker compose up -d` fail clearly on its own at `postgres`/`fibergate-core` if missing (empty-credential error) — enough of a signal for a merchant, no need for an extra container just to check. Instructions for generating each secret (`openssl rand -hex 32`, `docker run --rm httpd:alpine htpasswd -nbBC 10 admin '...'`) moved from a comment in `.env.example` to a "Generating secrets" section in `README.md` — `.env.example` stays lean, and the detailed instructions get a dedicated, more readable spot. Live-verified: `docker compose up -d postgres` with an empty `POSTGRES_PASSWORD` — the official `postgres` image itself blocks this and prints a clear error ("Database is uninitialized and superuser password is not specified...") and restart-loops, a strong enough signal without a custom preflight.

[2026-07-02] **`fiber-node` publishes RPC loopback-only (`127.0.0.1:8227:8227`)** (human made the final call directly, after I analyzed the risk of publishing publicly and proposed binding loopback instead of leaving it unpublished or binding `0.0.0.0`): Initially `fiber-node` had no `ports:` at all (matching issue #3's requirement "not bind a public IP/port"), but the consequence was that `pnpm dev` (running `apps/web` outside Docker) couldn't reach `fiber-node` even while it was running — the `FIBER_NODE_URL=http://localhost:8227` value previously suggested in `apps/web/.env.example` actually didn't work since no port was published. Adding `"127.0.0.1:8227:8227"` solves exactly this problem without violating the original requirement: loopback-only binding never gets exposed outside the machine it runs on, even if that machine is a VPS with a public IP — very different from a plain `"8227:8227"` (defaults to `0.0.0.0`, which would expose the RPC — with Biscuit auth still off — to the internet). Live-verified: `docker compose ps` shows exactly `127.0.0.1:8227->8227/tcp`, `ss -tlnp` confirms the socket only LISTENs on `127.0.0.1`, not `0.0.0.0`. `apps/web/.env.example`'s `FIBER_NODE_URL=http://localhost:8227` can now be pre-filled since it genuinely works (previously left blank because it wasn't certain).

[2026-07-02] **Incident during the first real `docker compose up -d` run (issue #3 already merged but never run live by anyone) — 3 chained errors, resolved in sequence:**

Context: human ran `docker compose up -d` exactly per README, hit an error right at the first step. Each error was resolved in turn, each one masking the next until fully fixed:

1. **`fiber-node-preflight` exits 1 — "missing CKB testnet key"**: Exactly the intended preflight behavior (see the "Added the `fiber-node-preflight` service" decision above) — `docker/fiber-node/ckb/key` didn't exist yet. Not a bug, just an unfinished setup step.

2. **`ADMIN_PASSWORD_HASH` silently corrupted by Docker Compose via `.env` interpolation**: Alongside error 1, saw the warning `"The \"NdL\" variable is not set. Defaulting to a blank string."`. Cause: the bcrypt hash `$2y$10$NdL.ph3...` in `.env` contains multiple `$` characters (`$2y`, `$10`, `$NdL`), and Docker Compose auto-interpolates `$VAR`/`${VAR}` inside **the value stored in `.env`**, not just inside `docker-compose.yml` — every `$xxx` chunk was misread as an unset compose variable and silently replaced with an empty string. Verified via `docker compose config | grep ADMIN_PASSWORD_HASH`: the hash was missing the `NdL.` segment entirely, meaning dashboard login would definitely fail with zero clear error message at `up -d` time. Fix: escape every `$` in the hash value as `$$` (`ADMIN_PASSWORD_HASH=$$2y$$10$$NdL.ph3...`), re-verified via `docker compose config` that it resolves back to the exact original value. This is a different variant of the gotcha already documented in the "`CHANGE_ME_*` — DONE, THEN REVERTED" decision above (that time it was `$` inside a service's multi-line `command:` block; this time it's `$` inside the value of an ordinary `.env` variable, with no `command:` involved at all) — general conclusion: **any value placed in `.env` that contains a `$` character (a bcrypt hash being the most common example, could also be some base64/token) must be escaped as `$$`**, not just inside a service's `command:` block.

3. **`fiber-node` crash-loops: `Secret key file error: decryption failed: aead::Error`**: After adding the key to `docker/fiber-node/ckb/key`, `fiber-node-preflight` passed but `fiber-node` itself crash-looped with a decrypt error even though `FIBER_SECRET_KEY_PASSWORD` was confirmed correct (human verified with `ckb-cli account export --lock-arg ... --extended-privkey-path key2` using that exact password, export succeeded). So the error wasn't a wrong password but a **wrong file format**: `ckb-cli account export --extended-privkey-path` outputs a **2-line** file (line 1 = raw private key, line 2 = chain code of the extended key), while `fnn` only accepts **exactly 1 line of raw private key hex, no `0x` prefix, no chain code**. The key file still had both lines intact. Confirmed by measuring the file's size/line count (without printing the key contents to the terminal): `wc -c` = 129 bytes = 2 lines × 64 hex chars + 1 newline, matching the hypothesis. Fix: `head -n 1 docker/fiber-node/ckb/key > tmp && mv tmp docker/fiber-node/ckb/key && chmod 600 ...` — keeping only the first line.

4. **`fiber-node` runs (`secret key migration done`) but the RPC server refuses to start — "Cannot listen on a public address without a biscuit public key set in the config"**: The root cause was `docker/fiber-node/config.yml`'s `rpc.listening_addr: 0.0.0.0:8227` — this value was set intentionally per the "build strategy" decision above with the reasoning "so sibling containers can reach it over the internal docker network," which worked correctly during code review but had **never actually run live to this step**, so the problem hadn't surfaced. `fnn` (the pinned `0.9.0-rc6` build) hard-enforces at startup: it refuses to bind any address it classifies as "public" unless `rpc.biscuit_public_key` is set. Confirmed via 2 sources: (a) the real runtime error log; (b) querying CKB AI MCP (`mcp__ckb-ai__search_resources` → `ReadMcpResourceTool` reading `ckb://docs/fiber/node-setup`, "Safe RPC Exposure" section) — verbatim: *"Hard rule, enforced at startup: the node refuses to start if `rpc.listening_addr` is a public address and `rpc.biscuit_public_key` is not set... A 'public address' is anything not loopback / private / link-local (including `0.0.0.0`)."* — meaning **`0.0.0.0` is classified by `fnn` as "public" even though it's actually only running on an internal docker network with no route out** — the implicit assumption in the "build strategy" decision above ("binding internally means there's no need to worry about public/Biscuit anything") turned out to be wrong in practice, despite being right in security spirit.

   Considered 2 approaches, laid out the trade-offs clearly for the human before choosing:
   - **(a) Set up full Biscuit auth**: the mechanism `fnn` is actually designed for non-loopback binding (generate an ed25519 keypair, mint scoped tokens with `read`/`write` domains per RPC module). Checked and found the `nervos/fiber` image **doesn't bundle** any Biscuit gen/mint tool (`fnn --help`, `fnn-cli --help`, listing the image's binaries all come up empty) — would require installing an external tool (e.g. `biscuit-cli` via `cargo install` in a throwaway container), i.e. **adding a new dependency** (CLAUDE.md requires asking first) plus ongoing operational cost (managing/rotating tokens) for a connection that is **always purely internal to Docker** with no route out.
   - **(b) Assign a static private IP to `fiber-node`** instead of the wildcard `0.0.0.0`: `fnn`'s own troubleshooting table also hints at this ("...set it or bind to `127.0.0.1`" — using `127.0.0.1` isn't viable here since that's loopback *inside* the `fiber-node` container, unreachable by any other container (`fibergate-core`); what's needed is an IP in a private range that sits on a real network interface reachable by other containers — i.e. that container's own IP on the bridge network). No new dependency, effective security unchanged (still 0 routes out of the internal docker network, exactly as with `0.0.0.0`).

   Human chose (b) — Reason: keep scope minimal in the spirit of the hackathon, avoid adding a dependency/operational burden disproportionate to the benefit for a connection that is never public. Implementation: `docker-compose.yml`'s `fibergate-net` network gets `ipam.config.subnet: 172.28.0.0/24`; the `fiber-node` service gets `networks.fibergate-net.ipv4_address: 172.28.0.10`; `docker/fiber-node/config.yml`'s `rpc.listening_addr` changed from `0.0.0.0:8227` → `172.28.0.10:8227`. This cascaded into another fix needed: the healthcheck `["CMD", "fnn-cli", "info"]` (defaults to targeting `127.0.0.1`, run *inside* the `fiber-node` container itself) could no longer reach the RPC since it now binds strictly to `172.28.0.10`, not a wildcard anymore — changed to `["CMD", "fnn-cli", "-u", "http://172.28.0.10:8227", "info"]`. `FIBER_NODE_URL=http://fiber-node:8227` (the variable `fibergate-core` uses to call across) **did not need to change** — it resolves via Docker DNS by service name, independent of whether the IP is static or dynamic, exactly like `POSTGRES_HOST=postgres` had already been working.

   Live-verified: `docker compose up -d` → `docker compose ps` shows `fiber-node` "healthy" (previously "unhealthy"/exited); `docker compose logs fiber-node` confirms the sequence `secret key is using plain key format, start migrating to encrypted format` → `secret key migration done` → RPC started successfully, no more biscuit error logs; all 3 containers (`postgres`, `fiber-node`, `fibergate-core`) are "healthy"/"running", `fibergate-core` logs `Ready in 96ms`.

   **Follow-up work** (not done in this session): sync `system-design.md` (the line stating `rpc.listening_addr: 0.0.0.0:8227` in the "fiber-node container" section, and the assumption "binding internally means Biscuit auth can be turned off entirely" in the websocket subscription section — both are based on the old design and are now wrong) and add the 3 gotchas above (preflight, `$` escaping, single-line key file, static IP/biscuit) to `README.md`'s Troubleshooting.

[2026-07-03] **`postgres` publishes its port loopback-only (`127.0.0.1:5432:5432`) — discovered when the human tried running `pnpm --filter web db:migrate` after issue #4 was merged**: The `postgres` service in `docker-compose.yml` previously had no `ports:` at all (only reachable within the internal `fibergate-net` network), so `pnpm --filter web db:migrate`/`pnpm dev` running on the host (`POSTGRES_HOST=localhost` per `apps/web/.env.local`) couldn't connect — verified by testing the `localhost:5432` socket from the host: connection refused. Further investigation found running the migration from **inside** the `fibergate-core` container also didn't work: `docker/fibergate-core/Dockerfile` builds production via `output: standalone`, which doesn't copy `apps/web/lib/db/migrations/` and doesn't install `drizzle-kit` (devDependency stripped out). [2026-07-05] **`ADMIN_PASSWORD_HASH` → `ADMIN_PASSWORD_HASH_B64` (issue #9, after PR #32 merged) — discovered while the human tested login via `pnpm dev`, not via `docker compose up -d`:**

Human found `bcrypt.compare()` failing despite a correct password when running `pnpm dev` locally, using a hash already verified correct with a direct `bcrypt.compareSync()` (a separate test script). Deeper investigation found this was **not** simply a case of forgetting to escape `$$` like the bug documented on 2026-07-02 — it was a genuine architectural conflict between two mechanisms both reading the same root `.env`:

- **Docker Compose**: auto-interpolates `$VAR`/`${VAR}` inside `.env` values, treating `$$` as a valid escape for a literal `$` (verified against a real container via `docker compose run --rm test printenv TESTVAR` — **not just trusting `docker compose config`'s output**, since that command re-escapes `$` when displaying the YAML, which can look correct even when the real runtime value is wrong). Result: `$$2y$$10$$abc` in `.env` → correctly becomes `$2y$10$abc` inside the container.
- **`dotenv-expand`** (a dependency of `dotenv-cli`, used by all 4 scripts `dev`/`build`/`db:generate`/`db:migrate`): also auto-interpolates `$VAR` but with a different algorithm, which does **not** treat `$$` as an escape — both the raw value (`$2y$10$abc`) and the escaped value (`$$2y$$10$$abc`) get corrupted (a chunk of characters is lost partway through), differing only in which chunk gets lost.

Tried 2 workarounds before concluding there's no shared escaping scheme: (a) `dotenv-cli`'s `--no-expand` flag — makes the raw value pass through correctly, but the `$$`-escaped value (needed for Docker) is still wrong (doesn't auto-collapse); (b) Docker Compose's `env_file:` directive instead of `environment: ${VAR}` — verified against a real container, still corrupted identically, since Compose applies interpolation to **every** way of reading `.env`, not just the one currently in use.

Presented 3 fix directions to the human before choosing: (a) base64-encode the value in `.env` (the base64 alphabet has no `$`, sidestepping both mechanisms entirely); (b) add `--no-expand` + accept that `pnpm dev` needs a different value than Docker, breaking the "single `.env` file" decision (2026-07-02); (c) just document the limitation, no code change, accepting that login can't be tested via `pnpm dev`.

**Human chose (a)** — Reason: fixes the actual root cause (removing the `$` character from the value stored in `.env` entirely), no more escaping needed on either side, and doesn't break the "single `.env` file" decision. Implementation: renamed the env var to `ADMIN_PASSWORD_HASH_B64` (a new name so no one mistakenly pastes a raw hash into it — different enough from the old value that there's no backward-compatibility risk with any real hash currently in use), `README.md`'s "Generating secrets" gained a `| base64 | tr -d '\n'` step in the generation command, and `app/login/actions.ts` decodes with `Buffer.from(value, "base64").toString("utf-8")` before calling `bcrypt.compare()`. Known to be a stopgap fix for the env-var-only model — if issue #30 (moving `ADMIN_PASSWORD_HASH` to DB-backed storage) ships, this problem disappears entirely for day-to-day verification (Postgres/Drizzle doesn't care about `$`), leaving only a single seeding step at initial-data time that needs its own separate design.

[2026-07-06] **Webhook retry processing (issue #8, `BR-WHK-003`): kept separate from the invoice-status-detection mechanism, no queue engine used at the current scope** (confirmed directly by the human in conversation): handling attempt 2/3 (retrying once `next_retry_at` is due) is inherently **time-based**, not event-based — it needs to know "has 1 minute/5 minutes elapsed yet," and no blockchain event announces that on its own. This is quite different from "detect an invoice transitioning to a terminal state → fire attempt 1 immediately" (event-driven: a poller diff in Phase 1, a WebSocket `subscribe_store_changes` handler in Phase 2) — these two concerns should stay separate in the code even though in Phase 1 they happen to share a single interval timer. RETURNING`, equivalent to `SELECT ... FOR UPDATE SKIP LOCKED`) should be used to prevent 2 instances processing the same delivery, rather than switching to a new queue dependency.

[2026-07-06] **Update/supersede the retry-processing decision right above (issue #8, see `harness-brief.md`'s "Resolved decisions" #2 from run `.claude/harness/20260705T224919/`)**: after settling on the "separate interval scanner" direction in the entry right above, the conversation with the human continued and **switched to a different mechanism, fully replacing** the interval-scanner choice: a `setTimeout`-based scheduler (`apps/web/lib/webhooks/retry-scheduler.ts`'s `scheduleAttempt(deliveryId, delayMs)`) + a single one-time boot-recovery scan (`recoverPendingDeliveries()`, called from `instrumentation.ts` at process startup, scanning `WHERE status='pending' AND next_retry_at IS NOT NULL` exactly once) — no more recurring periodic interval scanner.
